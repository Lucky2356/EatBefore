# Разработка Android-приложения для домашнего учёта продуктов

Ты выступаешь как автономная команда разработки, включающая:

* senior Android-разработчика;
* backend-архитектора;
* UX/UI-дизайнера;
* специалиста по информационной безопасности;
* QA-инженера;
* продуктового аналитика.

Твоя задача — спроектировать и реализовать практически готовое к использованию Android-приложение для домашнего учёта продуктов.

Не создавай учебную демонстрацию, набор экранов-заглушек или поверхностный прототип. Создай полноценный, поддерживаемый, безопасный и расширяемый продукт, который после завершения можно устанавливать на Android-устройство, тестировать и постепенно публиковать.

Работай автономно. Не останавливайся после создания архитектуры или нескольких экранов. Последовательно реализуй приложение, запускай сборку, исправляй ошибки, добавляй тесты и обновляй документацию.

Если какое-либо требование невозможно реализовать полностью без внешнего сервиса, создай рабочий локальный вариант, предусмотрев интерфейс и архитектурную точку расширения для будущей реализации.

# 1. Концепция продукта

Приложение помогает пользователю учитывать продукты, которые находятся:

* в холодильнике;
* в морозильнике;
* в кухонном шкафу;
* в кладовой;
* в других пользовательских местах хранения.

Пользователь должен иметь возможность:

1. Отсканировать штрихкод, QR-код или DataMatrix.
2. Определить продукт по коду.
3. Добавить одну или несколько упаковок продукта в домашние запасы.
4. Указать срок годности вручную или распознать его по фотографии упаковки.
5. Видеть, какие продукты есть дома.
6. Получать уведомления о приближении срока годности.
7. Быстро отмечать, что продукт:

   * открыт;
   * частично использован;
   * закончился;
   * выброшен;
   * просрочен;
   * перемещён в другое место хранения.
8. Просматривать историю продукта и всех действий с ним.
9. Добавлять закончившийся продукт в список покупок.
10. Видеть аналитику покупок, потребления и выброшенных продуктов.
11. Добавлять продукты без штрихкода.
12. Учитывать домашние блюда, заготовки, овощи, фрукты и продукты с рынка.

Главная ценность приложения:

> Помочь пользователю помнить, какие продукты есть дома, вовремя использовать их, реже покупать лишнее и меньше выбрасывать еду.

# 2. Основные продуктовые принципы

## 2.1. Минимум действий

Пользователь не должен уставать от ведения учёта.

Любое частое действие должно занимать не более одного-двух нажатий:

* добавить продукт;
* повторно добавить ранее использованный продукт;
* отметить продукт закончившимся;
* отметить упаковку открытой;
* отправить продукт в список покупок;
* отменить последнее действие.

Не заставляй пользователя заполнять большие формы.

Используй:

* разумные значения по умолчанию;
* автозаполнение;
* последние использованные значения;
* шаблоны;
* быстрые кнопки;
* свайпы;
* контекстные действия;
* подтверждение только для потенциально опасных операций.

## 2.2. Работа без интернета

Основные функции должны работать полностью офлайн:

* просмотр запасов;
* добавление вручную;
* редактирование;
* история;
* уведомления;
* список покупок;
* аналитика;
* поиск;
* резервное копирование.

Интернет используется только для получения внешней информации о товаре по штрихкоду.

При отсутствии интернета пользователь всё равно должен иметь возможность сохранить продукт вручную.

## 2.3. Локальное хранение и конфиденциальность

На первом этапе приложение должно быть local-first.

Не требуй обязательной регистрации.

Не собирай персональные данные без необходимости.

Не добавляй рекламные SDK, скрытые трекеры или передачу данных третьим лицам.

Архитектура должна позволять позднее добавить:

* учётную запись;
* семейный доступ;
* облачную синхронизацию;
* несколько устройств;
* совместный список покупок.

Однако облачная синхронизация не должна быть жёстко встроена в локальную бизнес-логику.

# 3. Технологический стек

Используй нативную Android-разработку.

Предпочтительный стек:

* Kotlin;
* Jetpack Compose;
* Material 3;
* Clean Architecture без чрезмерного усложнения;
* MVVM или MVI с однозначным управлением состоянием;
* Room;
* Kotlin Coroutines;
* Flow;
* WorkManager;
* CameraX;
* актуальную поддерживаемую библиотеку для сканирования штрихкодов;
* актуальную поддерживаемую библиотеку OCR для распознавания дат;
* dependency injection;
* Navigation Compose;
* DataStore для настроек;
* Android Keystore для хранения чувствительных ключей;
* Gradle Version Catalog;
* unit-тесты;
* UI-тесты;
* static analysis и форматирование.

Перед подключением библиотек проверь актуальную официальную документацию и не используй устаревшие или deprecated API.

Не фиксируй секреты, API-ключи и токены в исходном коде.

Выбери разумную минимальную версию Android, поддерживающую современные API без чрезмерного ограничения аудитории.

# 4. Архитектура приложения

Используй модульную или хорошо разделённую архитектуру.

Пример логического разделения:

```text
app
core
  common
  database
  datastore
  designsystem
  notifications
  scanner
  network
  security
  testing
domain
data
feature
  onboarding
  home
  inventory
  scanner
  product
  history
  shopping
  analytics
  settings
```

Не создавай большое количество модулей только ради архитектуры. Если многомодульность сильно замедляет разработку, сначала используй понятное пакетное разделение, сохранив возможность последующего выделения модулей.

Соблюдай следующие правила:

* UI не обращается напрямую к Room или сетевому API.
* Бизнес-логика не зависит от Android Framework.
* Репозитории имеют интерфейсы.
* Внешний каталог товаров подключается через отдельный provider-интерфейс.
* OCR подключается через отдельный интерфейс.
* Уведомления не должны быть связаны напрямую с UI.
* Все операции изменения запасов создают записи в истории.
* Для базы данных должны поддерживаться миграции.
* Удаление пользовательских данных не должно выполняться без явного подтверждения.

# 6. Основные пользовательские сценарии

## 6.1. Первоначальный запуск

Создай короткий onboarding не более чем из трёх экранов.

Объясни:

* что приложение хранит данные локально;
* как сканировать продукты;
* зачем нужны уведомления;
* что продукт можно добавить вручную.

После onboarding пользователь сразу попадает на главный экран.

Не требуй регистрации.

Разрешения камеры и уведомлений запрашивай только в подходящий момент, объясняя, зачем они нужны.

## 6.2. Главный экран

Главный экран должен сразу показывать полезную информацию:

* продукты, которые скоро испортятся;
* общее количество продуктов;
* быстрые действия;
* выбранное место хранения;
* недавно добавленные продукты;
* список критических уведомлений.

Главная кнопка действия — сканирование.

Дополнительные быстрые действия:

* добавить вручную;
* открыть список покупок;
* посмотреть продукты с истекающим сроком;
* повторить последнюю покупку.

Не перегружай экран карточками и текстом.

## 6.3. Сканирование

Сканер должен:

* быстро запускаться;
* иметь подсветку области сканирования;
* поддерживать фонарик;
* предотвращать многократное чтение одного кода;
* иметь понятную вибрацию или анимацию успешного сканирования;
* разрешать ввод кода вручную;
* работать при повороте устройства;
* корректно обрабатывать отказ в доступе к камере.

После сканирования:

1. Найди товар в локальном кеше.
2. При необходимости запроси внешний каталог.
3. Покажи компактную карточку найденного продукта.
4. Предложи:

   * количество;
   * место хранения;
   * срок годности;
   * фотографирование срока годности.
5. Добавь продукт одним подтверждением.

Если товар уже есть:

> Этот продукт уже находится в холодильнике. Добавить ещё одну упаковку?

## 6.4. Определение срока годности

Не предполагай, что обычный EAN-код содержит срок годности.

Поддержи следующие варианты:

1. Извлечение данных из QR/DataMatrix, если код действительно содержит дату или структурированные поля.
2. OCR по фотографии упаковки.
3. Ручной выбор даты.
4. Быстрые варианты:

   * сегодня;
   * завтра;
   * через 3 дня;
   * через неделю;
   * через месяц;
   * без срока.
5. Использование последнего срока или шаблона для часто добавляемого товара.

OCR должен:

* искать несколько распространённых форматов дат;
* учитывать обозначения «годен до», «использовать до», «дата изготовления»;
* не сохранять дату без подтверждения пользователя;
* показывать исходный распознанный текст;
* позволять исправить результат.

Если OCR не уверен в результате, не выдавай догадку за точное значение.

## 6.5. Карточка продукта

Покажи:

* изображение;
* название;
* производителя;
* количество;
* срок годности;
* оставшееся время;
* место хранения;
* состояние;
* дату открытия;
* историю действий.

Быстрые действия:

* открыть;
* уменьшить количество;
* закончилось;
* выбросить;
* переместить;
* изменить;
* добавить в покупки.

## 6.6. Частичное использование

Поддержи два режима:

### Простой режим

* есть;
* открыто;
* закончилось;
* выброшено.

### Подробный режим

* штуки;
* граммы;
* килограммы;
* миллилитры;
* литры;
* упаковки;
* проценты остатка.

По умолчанию используй простой режим.

Подробный режим пользователь включает в настройках или непосредственно в карточке продукта.

## 6.7. История

История должна позволять:

* видеть все действия;
* фильтровать по продукту;
* фильтровать по типу события;
* фильтровать по дате;
* восстановить случайно списанный продукт;
* отменить последнее действие;
* повторно добавить ранее использованный продукт.

## 6.8. Список покупок

При списании продукта предложи:

> Добавить в список покупок?

В списке покупок должны быть:

* отметка выполнения;
* группировка по категориям;
* количество;
* быстрый возврат товара в запасы после покупки;
* ручное добавление;
* повторение регулярных покупок.

## 6.9. Аналитика

Создай понятную пользовательскую аналитику:

* сколько продуктов добавлено;
* сколько употреблено;
* сколько выброшено;
* сколько просрочено;
* какие категории чаще выбрасываются;
* какие товары покупаются регулярно;
* потенциально предотвращённые пищевые отходы.

Не создавай псевдоточную финансовую аналитику, если пользователь не указывает цены.

# 7. Уведомления

Используй WorkManager и корректно учитывай ограничения Android.

Уведомления:

* срок истекает через несколько дней;
* срок истекает завтра;
* срок истекает сегодня;
* продукт уже просрочен;
* открытый продукт нужно использовать;
* давно не подтверждались запасы.

Пользователь должен иметь возможность настроить:

* время уведомлений;
* количество дней до срока;
* категории уведомлений;
* тихие часы;
* отключение уведомлений для отдельных продуктов.

Не отправляй слишком много уведомлений.

Объединяй их:

> Сегодня стоит проверить 4 продукта.

Не создавай ежедневный спам.

# 8. UX/UI и дизайн

Дизайн должен быть современным, спокойным, дружелюбным и не перегруженным.

Используй Material 3, но создай собственную целостную дизайн-систему.

Требования:

* светлая и тёмная темы;
* динамические цвета Android, если доступны;
* приятная натуральная цветовая палитра;
* хорошая читаемость;
* понятные иконки;
* крупные зоны нажатия;
* минимум мелкого текста;
* визуальные статусы срока годности;
* плавные, но короткие анимации;
* skeleton/loading states;
* empty states;
* error states;
* undo через Snackbar;
* подтверждение опасных действий;
* доступность для пользователей с нарушением зрения.

Не обозначай статус только цветом. Добавляй текст или иконку.

Пример визуальных состояний:

* свежий;
* скоро закончится срок;
* срок истекает сегодня;
* просрочен;
* открыт;
* количество заканчивается.

Поддержи системный размер шрифта и экранные дикторы.

Основная навигация:

* Главная;
* Запасы;
* Сканер;
* Покупки;
* Ещё.

Сканер может быть центральной выделенной кнопкой.

Реализуй:

* поиск по названию;
* поиск по бренду;
* поиск по штрихкоду;
* фильтр по месту хранения;
* фильтр по категории;
* фильтр по сроку годности;
* фильтр по статусу;
* сортировку по сроку, названию и дате добавления.

Поиск должен работать быстро на локальной базе.

# 10. Внешний каталог товаров

Создай абстракцию:

```kotlin
interface ProductCatalogProvider
```

Она должна позволять позднее менять источник данных.

Для первой реализации можно подключить открытый каталог товаров, но обязательно:

* использовать только разрешённые публичные API;
* учитывать rate limits;
* добавлять таймауты;
* кешировать ответы;
* корректно обрабатывать отсутствие товара;
* не считать внешние данные полностью достоверными;
* разрешать пользователю исправлять найденную информацию;
* не блокировать добавление продукта при ошибке API.

Не связывай доменную модель напрямую с DTO внешнего сервиса.

# 11. Безопасность

Проведи threat modeling и создай `THREAT_MODEL.md`.

Учитывай:

* подмену ответов внешнего API;
* вредоносные данные в QR-кодах;
* слишком длинные значения;
* попытки SQL-инъекций;
* path traversal при импорте и экспорте;
* подмену файлов резервных копий;
* утечку локальных данных;
* случайное удаление;
* хранение секретов;
* небезопасные deep links;
* небезопасную обработку изображений;
* чрезмерное потребление памяти;
* вредоносные или повреждённые изображения;
* повторные запросы;
* некорректные даты;
* переполнение чисел;
* гонки при одновременном изменении данных.

Обязательные требования:

* валидация всех внешних данных;
* ограничение размера изображений и импортируемых файлов;
* безопасная обработка URI;
* отсутствие произвольного выполнения содержимого QR-кода;
* QR-код рассматривается как данные, а не как команда;
* HTTPS для сетевых запросов;
* отсутствие логирования секретов и чувствительных данных;
* защита release-сборки;
* backup/export только по явному действию пользователя;
* безопасные миграции базы;
* защита от двойного нажатия и повторного добавления;
* обработка ошибок без утечки технических деталей пользователю.

Не запрашивай лишние Android-разрешения.

# 12. Производительность и оптимизация

Приложение должно быстро работать на устройствах среднего уровня.

Требования:

* холодный запуск без ненужных сетевых запросов;
* ленивые списки;
* пагинация или ограниченная загрузка больших историй;
* индексы Room для часто используемых запросов;
* фоновые операции вне главного потока;
* сжатие изображений;
* создание thumbnail;
* кеширование каталога товаров;
* debounce поиска;
* отсутствие бесконечных recomposition;
* стабильные ключи списков;
* отсутствие утечек Context;
* корректная отмена coroutine;
* разумные WorkManager-задачи;
* отсутствие фоновых циклов постоянного опроса;
* отсутствие ненужных wake lock;
* пакетная обработка уведомлений;
* профилирование основных сценариев.

Создай документ `PERFORMANCE.md` с бюджетами производительности.

* предупреждение перед заменой данных;

# 14. Обработка ошибок

Для каждого сценария создай понятное пользовательское сообщение.

Примеры:

* товар не найден;
* нет интернета;
* камера недоступна;
* код повреждён;
* дата не распознана;
* доступ к уведомлениям запрещён;
* файл резервной копии повреждён;
* недостаточно памяти;
* операция не выполнена.

Не показывай пользователю stack trace.

Добавь повтор операции там, где это безопасно.

# 19. Критерии готовности

Проект считается готовым, когда:

* приложение успешно собирается;
* создаётся устанавливаемый debug APK;
* основные сценарии работают без интернета;
* сканер обрабатывает реальные коды;
* неизвестный товар можно добавить вручную;
* один товар может иметь несколько партий с разными сроками;
* все операции отображаются в истории;
* случайное списание можно отменить;
* уведомления не дублируются;
* приложение не падает при отказе в разрешениях;
* приложение не падает при ошибках сети;
* база данных имеет миграции;
* отсутствуют секреты в репозитории;
* тесты проходят;
* lint не содержит критических ошибок;
* светлая и тёмная темы работают;
* данные можно экспортировать и восстановить;
* README содержит рабочие команды запуска;
* нет экранов-заглушек для функций P0;
* нет кнопок, которые ничего не делают;
* нет критических TODO в основном пользовательском потоке.

# 20. Ограничения и правила реализации

* Не создавай монолитный экран или один огромный ViewModel.
* Не помещай бизнес-логику в Compose-функции.
* Не используй глобальные mutable-состояния.
* Не усложняй архитектуру бессмысленными слоями.
* Не добавляй обязательный сервер.
* Не используй платные сервисы без необходимости.
* Не добавляй функции, ухудшающие конфиденциальность.
* Не сохраняй OCR-изображения бесконечно без необходимости.
* Не выполняй команды, ссылки или скрипты из QR-кодов.
* Не используй нестабильные экспериментальные API без обоснования.
* Не оставляй проект в состоянии, когда код написан, но не собирается.
* Не заканчивай работу после создания документации.
* Не заявляй о готовности функции, пока она не реализована и не проверена.

При выборе между сложным и простым решением выбирай самое простое решение, которое остаётся безопасным, тестируемым и расширяемым.
