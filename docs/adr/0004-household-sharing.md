# ADR-0004: Совместный доступ к запасам (двое и более в одном доме)

Статус: **реализовано (этап 1, вариант A)** · Дата: 2026-07-16, обновлено 2026-07-23

## Контекст

Приложение local-first: вся база лежит на устройстве, без регистрации и серверов.
Нужно, чтобы **два человека (семья) видели одни и те же продукты** и изменения друг
друга. Ограничения: не ломать приватность (никаких обязательных аккаунтов и наших
серверов), сохранить офлайн-работу, не превратить P0-приложение в распределённую
систему за один шаг.

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Общий файл в облаке пользователя** (Google Drive/Dropbox через SAF: приложение периодически пишет/читает файл-журнал) | Без своих серверов; данные у пользователя; просто | Конфликты при одновременной записи; задержка синхронизации; зависимость от стороннего диска |
| **B. Синхронизация по локальной сети** (Wi-Fi Direct / mDNS + локальный обмен журналом событий) | Полностью приватно, быстро дома | Оба устройства должны быть в одной сети одновременно; сложная отладка |
| **C. Собственный облачный бэкенд** (аккаунты, push) | Настоящий realtime, вне дома | Серверы, аккаунты, стоимость, приватность — противоречит local-first |
| **D. Ручной обмен бэкапами** (уже реализовано: экспорт/импорт JSON) | Уже работает | Импорт затирает данные получателя; неудобно как постоянный режим |

## Решение

Ключевое преимущество нашей схемы данных: **история запасов — append-only журнал
`InventoryEvent`**. Это делает слияние двух устройств детерминированным: события
объединяются по (uuid, createdAt), состояние партии — производная от журнала.
Поэтому синхронизация строится как **обмен журналами событий (event log sync)**, а
не как слияние таблиц.

Поэтапно:

1. **v1.1 — вариант A (общий файл-журнал)**: устройство добавляет свои новые события
   в общий файл на диске пользователя (через SAF можно выбрать папку Google Drive /
   Яндекс.Диска), при открытии приложения подтягивает чужие. Конфликты решаются
   правилами: события не редактируются; «последний по времени статус» побеждает;
   количество — по последнему событию. Для идентификации устройств событиям
   добавляется `deviceId`, продуктам/партиям — стабильные `uuid` (миграция схемы).
2. **v1.2 — вариант B (локальная сеть)** поверх той же механики журнала: тот же
   формат обмена, другой транспорт (mDNS-обнаружение + локальный HTTPS).
3. Вариант C не делаем, пока пользователи явно не попросят синхронизацию вне дома;
   если попросят — рассматривать сторонние E2E-хранилища, а не свой бэкенд.

## Что реализовано (2026-07-23)

Этап 1 готов. Отклонения от первоначального плана и их причины:

- **Не один общий файл, а по файлу на устройство** — `journal-<deviceId>.json`.
  Каждое устройство пишет только свой файл и читает чужие. Один общий файл, в
  который все дописывают, потребовал бы блокировки, а её через облачный диск
  просто нет: два телефона, пишущие одновременно, затёрли бы правки друг друга.
- **`deviceId` у локальных событий пустой.** Свой идентификатор проставляется в
  момент публикации журнала, поэтому обычная запись события не делает
  асинхронный запрос за ним. Непустое значение означает «пришло от соседа» —
  ровно то, что нужно слиянию.
- **Разрешение конфликтов**: события неизменяемы и пропускаются по уже
  известному uuid (повторная синхронизация — no-op); партии — «побеждает
  свежий `updatedAt`», поэтому устаревший телефон не воскресит съеденное;
  места хранения сопоставляются по имени, а не по uuid.
- **Побочный выигрыш**: uuid в схеме закрыли давнее ограничение импорта —
  партии больше не дублируются при повторном импорте одного файла.

Файлы: `core/sync/` (`SyncEngine` — слияние, `SyncManager` — SAF-папка,
`SyncWorker`/`SyncScheduler` — периодический обмен раз в 6 часов), миграция
`MIGRATION_1_2`, раздел «Совместный доступ» в настройках.

Ограничения, о которых сказано пользователю прямо в интерфейсе: обмен не
мгновенный — сначала папку должен синхронизировать облачный диск, а второй
телефон открыть приложение.

## Последствия

- Требуется миграция Room: `uuid` для products/batches/events, `deviceId` в events —
  закладывается до начала реализации v1.1.
- Экспорт/импорт (уже в проде) остаётся аварийным способом переноса и основой
  формата обмена (тот же сериализатор).
- UI: раздел настроек «Совместный доступ» — выбор папки синхронизации, статус
  последнего обмена, список устройств.
